# Сервер закрытой беты — 0.21.0

26.10.2026. По запросу пользователя серверная часть реализуется до завершения наблюдений этапа E, чтобы проводить бета-тест на опубликованном сайте. Публичная площадка и домен ещё не выбраны.

## Что работает

- Один Node.js 24 сервер, встроенный SQLite, постоянный диск и версия схемы базы. npm-зависимостей нет.
- Семь заранее созданных аккаунтов: `admin` и `beta01`–`beta06`, шесть из них — участники. Пароли случайные, по 24 символа; регистрация закрыта. Создание повторно не сбрасывает учётные данные.
- Сохранение всех 11 разделов учебного прогресса и отдельного журнала наблюдений. Состояние записывается примерно раз в три секунды при изменении и вручную кнопкой. Сервер повторно проверяет архив через существующие модели и рассчитывает сводку 22 шагов.
- Аккаунты изолированы в API и в браузерном кеше. Перенос прежнего JSON в выбранный аккаунт остаётся явным действием; автономные сохранения не присваиваются первому вошедшему пользователю.
- Повтор запроса с тем же идентификатором не создаёт ещё одну запись. Устаревшая версия получает 409. Автозапись останавливается; интерфейс позволяет скачать данные либо сохранить свою ветку отдельной серверной копией и загрузить актуальную. Учебный JSON затем объединяется через существующий перенос. Журналы наблюдений восстанавливаются отдельно.
- До десяти отдельных конфликтных копий пользователя без автоматического обрезания; пять последних предыдущих серверных состояний для технического восстановления. Достижение лимита отдельных копий сообщает об ошибке и не переписывает данные.
- Администратор видит шесть участников, последний серверный прогресс, время сохранения, 22 шага, самостоятельные условия, помощь и ошибки практики, переданные наблюдения. Он не редактирует чужие результаты через веб-интерфейс.
- Выход отзывает сессию. При непереданных изменениях предложены скачивание и отдельное подтверждение выхода; локальная работа остаётся связана с тем же аккаунтом. Сброс пароля выполняется через CLI организатора, с отзывом сессий и сохранением учебных результатов.

## Защита доступа

Пароли хранятся как scrypt с уникальной солью (`N=32768, r=8, p=3`), а не в открытом виде. Параметры соответствуют одному из минимальных вариантов [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Закрытый файл начальной выдачи хранится отдельно и не включается в исходники или Docker image.

Вход ограничен по нормализованному аккаунту независимо от IP: после пяти неудач — временная задержка, при продолжении она увеличивается до 15 минут в рамках окна. По IP — не более 120 запросов входа за 15 минут. Счётчики находятся в SQLite и переживают перезапуск. Бессрочной автоматической блокировки нет; администратор сервера может сбросить пароль и ограничения. Временное ограничение известного логина может использоваться для задержки входа владельца; это компромисс защиты от распределённого подбора, а не механизм гарантированной доступности.

Сессии имеют случайные непрозрачные токены; в базе сохраняется только их SHA-256. В production используются `__Host-` cookie с `HttpOnly`, `Secure`, `SameSite=Strict`, без `Domain`. Срок — до 12 часов и до двух часов без запросов; у пользователя не больше пяти активных сессий. Локальная HTTP-разработка разрешена только на loopback. Production отказывается стартовать с HTTP origin.

Изменения требуют точного Origin и CSRF-токена. Подставленный идентификатор другого пользователя не меняет владельца записи. Ответы API не раскрывают хеши паролей или сессий; сообщения неверного логина/пароля одинаковы. Добавлены CSP, запрет фреймов и MIME sniffing, HSTS в HTTPS-режиме, ограничения размеров тел, одновременного чтения и вычисления паролей, частоты изменений. Статические файлы выдаются по закрытому списку: база, пароли, исходники сервера, тестовые решения и `.env` недоступны через HTTP. Подход основан на [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) и [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Caddy перезаписывает IP-заголовок, а сервер дополнительно проверяет адрес непосредственного прокси. App не имеет внешнего опубликованного порта в compose; сеть приложения и копий изолирована от внешней сети. Входящий IP из произвольного пользовательского заголовка не принимается.

## Данные и восстановление

SQLite использует WAL, полную синхронизацию и транзакции. Миграция схемы и начальная служебная запись атомарны. Перенос в кеше происходит через журнал транзакции до запуска контроллеров. Кеш разнесён по UUID аккаунта; смена аккаунта на сервере не позволяет старой вкладке отправить его данные под новым владельцем.

Исправлена выявленная в ручном прогоне гонка: после импорта старого JSON контроллеры ещё содержат прежние данные до перезагрузки. Синхронизатор теперь останавливает сбор такого состояния при смене локальной ревизии и сохраняет признак неотправленного импорта. Есть автоматическая регрессионная проверка. Откат серверной базы к более ранней ревизии также вызывает разбор конфликта вместо очистки более нового кеша.

Docker Compose включает Caddy, приложение и резервирование. Проверенная копия создаётся сразу и затем раз в сутки, до 14 локальных копий; при ошибке повтор через 10 минут. Копии имеют отдельный volume и healthcheck. CLI умеет делать онлайн-копию SQLite и офлайн-восстановление с проверкой источника, предварительной копией текущей базы и отзывом сессий. Для потери всего VPS нужна ещё копия вне него, которая настраивается после выбора площадки.

## Что проверено

- Все 20 прежних наборов `npm test` проходят.
- Три новых набора `npm run test:server`: API/защита/база, изоляция кеша, настоящий клиент синхронизации с контролируемым DOM/сетью. Проверены роли, CSRF/Origin, временные ограничения после рестарта, недоверенный прокси, подмена IP, неверные архивы, размеры запроса, идемпотентность, конфликты, срок сессии, выход, онлайн-копия и офлайн-восстановление, гонка импорта и откат базы.
- Обе автономные сборки и проверка 39 курсовых скриптов, дополнительных серверных и клиентских файлов проходят. CI обновлён до Node.js 24 и серверных проверок; удалённый CI не запускался.
- Ручной браузерный прогон на отдельной базе: вход `beta01`, перенос прежнего архива 22/22, перезагрузка и подтверждение сохранения; выход и вход `beta02` даёт 0/22; администратор видит шесть участников и 22/22 у первого, открывает подробный разбор. Это служебные данные, не результаты реальных учеников.
- Docker image собран и запущен непривилегированно с корнем только для чтения; health endpoint отвечает, семь аккаунтов сохранились после рестарта контейнера. Отдельная резервная копия из read-only volume базы создана и проверена.
- Полный compose с Caddy/приватной сетью/backup запущен на локальном тестовом HTTP-порту. Вход и чтение семи аккаунтов через Caddy проверены HTTP-клиентом. Production Caddyfile прошёл `caddy validate`.

Локальный Node: 24.17.0; проверенный Docker image `node:24-alpine` содержал 24.21.0. Реальное публичное HTTPS, целевые устройства участников, внешний мониторинг/резервирование и поведение при большой нагрузке ещё не проверены.

## Где запускать

Локальная бета: `npm run beta:start`, **http://127.0.0.1:4180/**. Прежний адрес 4173 — автономная версия разработки, без серверной авторизации. Файл локальных учётных данных находится в `outputs/cnc-beta-accounts.private.json` за пределами репозитория; он не включается в выпуск.
