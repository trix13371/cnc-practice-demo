# Размещение закрытой бета-версии 0.21

Подготовлено 26.10.2026. Один сервер приложения, SQLite на постоянном диске, Caddy перед приложением и отдельный процесс ежедневных резервных копий. Публичный домен пока не выбран; интернет-публикация и выдача настоящего TLS-сертификата ещё не проводились.

## Что требуется

- Linux VPS с Docker Engine и Docker Compose v2. Практичный старт для семи аккаунтов: 1–2 vCPU, 2 ГБ RAM, 25–30 ГБ SSD/NVMe. Это инженерная стартовая оценка, а не результат нагрузочного теста большой группы.
- Домен или поддомен с A-записью на публичный IPv4 VPS. Открытые входящие TCP 80/443. Запись AAAA добавлять только при настроенном IPv6.
- Один экземпляр приложения и постоянные Docker volumes. SQLite не размещать на сетевой файловой системе или временном диске.

Docker для Ubuntu: [официальная инструкция](https://docs.docker.com/engine/install/ubuntu/). Конфигурация проекта не требует установки npm-зависимостей: используются встроенные модули Node.js 24.

## Первый запуск на VPS

Команды ниже — для Linux, из распакованного каталога `cnc-practice-demo`. Файл с паролями и локальная база в архив исходников не входят: на новом сервере создаются новые уникальные пароли.

```sh
cp .env.example .env
# Откройте .env и замените DOMAIN=beta.example.com своим доменом.
docker compose build --pull
docker compose run --rm app node server/cli.cjs init
docker compose up -d
docker compose ps
```

Инициализацию выполняют один раз до первого запуска. Повторная команда не пересоздаёт пользователей и не сбрасывает их пароли. После запуска открывайте `https://ВАШ-ДОМЕН/`. Для выпуска сертификата Caddy домен должен указывать на этот VPS, а порты 80/443 — быть доступны извне. Домен и VPS оплачиваются отдельно от проекта.

Пароли заберите в закрытую папку:

```sh
mkdir -p secrets
chmod 700 secrets
docker compose cp app:/data/initial-access.private.json ./secrets/beta-accounts.private.json
chmod 600 ./secrets/beta-accounts.private.json
# После успешного получения закрытой копии уберите файл выдачи из контейнера:
docker compose exec -T app node -e "require('node:fs').unlinkSync('/data/initial-access.private.json')"
```

Файл выдачи паролей не нужен работающему приложению. Храните полученную копию отдельно, с доступом только организатору. На действующем Beget первоначальный файл уже перенесён в закрытый каталог root за пределами контейнеров; локальная копия организатора сохранена.

Проверка учебных архивов выполняется в отдельном worker с лимитом времени 2 секунды и ограниченной памятью. Один worker обрабатывает сохранение, ещё два запроса могут ждать. Перегрузка возвращает 503, слишком сложный архив — 422; база при этом не изменяется, клиент сохраняет локальную работу. Это защищает основной HTTP-процесс от дорогого повторного проигрывания журналов. Крупные старые архивы следует отдельно проверять перед массовым переносом.

Аккаунты: `admin`, `beta01` … `beta06`. Организатору нужен весь файл; каждому участнику выдаётся только его собственная строка. В файл исходников, Git и общую ссылку для участников пароли не публиковать. При переносе текущей локальной базы на VPS вместо создания новой необходимо отдельно перенести проверенную копию базы и права на неё.

## Как устроено размещение

Внешние порты открыты только у Caddy. Приложение и резервирование находятся в приватной сети Docker. Приложение принимает сведения об IP клиента только от IP самого Caddy (`172.30.81.2`), а Caddy перезаписывает заголовок входящего клиента. Клиентский заголовок не даёт выбрать произвольный IP для обхода ограничений.

Если подсеть `172.30.81.0/24` уже занята на VPS, поменяйте её и три адреса в `compose.yaml`, включая `TRUST_PROXY_PEERS`. При использовании другого reverse proxy нужно явно настроить его адрес в `TRUST_PROXY_PEERS` и перезапись `X-CNC-Client-IP`; наружу порт приложения не публиковать. Поведение Caddy описано в [официальной документации reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

Приложение работает от непривилегированного пользователя, с файловой системой образа только для чтения. Запись разрешена в volume `/data`; резервные копии — в отдельном volume `/backups`. Volume базы называется `cnc-beta_beta_data`, копий — `cnc-beta_beta_backups`. Имя проекта фиксировано `cnc-beta`; при использовании `-p` имена volumes получают другой префикс.

## Обновление

Перед обновлением создайте ручную проверенную копию:

```sh
docker compose exec -T app node server/cli.cjs backup --to /data/before-update.sqlite
docker compose cp app:/data/before-update.sqlite ./secrets/before-update.sqlite
docker compose build --pull
docker compose up -d
docker compose ps
```

Имя ручной копии должно быть новым: CLI не перезаписывает существующий файл. Обновление сохраняет volumes и аккаунты. Старые схемы и архивы проверяются; более новая неподдерживаемая схема базы блокирует запуск вместо очистки.

## Резервирование и восстановление

Сервис `backup` делает первую проверенную копию после запуска, затем каждые 24 часа; сохраняются последние 14 локальных копий. Ошибка вызывает повтор через 10 минут. Статус последней успешной копии проверяется healthcheck; состояние и ошибки видны в `docker compose ps` и `docker compose logs backup`. Ручная команда `backup` работает при запущенном приложении.

Эти volumes находятся на одном VPS. Чтобы пережить потерю всего VPS, включите резервирование у провайдера или регулярно сохраняйте отдельную проверенную копию вне сервера. Доступ к внешнему хранилищу пока не настраивался.

Восстановление из ежедневной копии:

```sh
# Остановить контейнеры, сохранив volumes.
docker compose down
docker compose run --rm --volume cnc-beta_beta_backups:/backups:ro app \
  node server/cli.cjs restore --from /backups/ИМЯ-КОПИИ.sqlite
docker compose up -d
```

Не добавляйте `-v` к `down`: этот флаг удаляет volumes с базой и копиями. CLI проверяет целостность и схему источника, сохраняет предыдущую базу, исключает параллельный запуск приложения во время восстановления и отзывает все сессии. Затем участники входят заново. Если устройство хранит более новую версию прогресса, интерфейс останавливает синхронизацию и предлагает сохранить отдельную копию.

При аварийном завершении процесса на той же машине устаревший `server.lock` распознаётся по процессу и времени его запуска. Неизвестный lock или lock другого контейнера требует проверки организатором: сначала убедитесь, что экземпляр приложения остановлен. Приложение не удаляет неоднозначный lock автоматически.

## Если участник забыл пароль

```sh
docker compose exec -T app node server/cli.cjs reset-password beta01
```

CLI сообщает путь нового закрытого файла, без вывода пароля в журнал. Заберите файл через `docker compose cp`. Прежние сессии этого пользователя отзываются; его учебные результаты остаются на месте. Самостоятельная регистрация и восстановление через email в этой бете не включены.

После получения защищённой копии файла нового пароля удалите исходный файл выдачи из контейнера. Он не нужен для входа: сервер проверяет только хеш в SQLite. Не удаляйте базу или файлы резервирования.

## Образы после проверки безопасности 26.10.2026

Dockerfile использует Node 24.22.1 без пакетных менеджеров в рабочем образе. Сервис caddy собирается из Dockerfile.proxy: Caddy 2.11.7, Go 1.27.3 и обновлённые зависимости. При первом запуске `docker compose build --pull` собирает оба образа; первая сборка прокси требует скачивания Go-модулей и нескольких минут. Проверка `caddy validate` и повторное сканирование описаны в SECURITY-2026-10-26.md. Следующие обновления безопасности требуют пересмотра закреплённых версий и повторной сборки.

## Минимальная проверка после публикации

Откройте адрес по HTTPS, войдите двумя разными участниками и убедитесь, что их результаты разделены. У администратора должна быть таблица шести участников. Сделайте действие в курсе, дождитесь «Прогресс сохранён в аккаунте», войдите тем же аккаунтом на другом устройстве и проверьте продолжение. Проверьте состояние `app` и `backup`, скачайте одну резервную копию. Это проверка уже выбранной площадки, которую нельзя заменить локальной сборкой Docker.
